# kind E2E Validation — 2026-09-01

## Environment

- kind `v0.33.0`
- Kubernetes node `v1.35.8`
- node image digest `sha256:07b2536e30b803ed61d1677a79df6115f798ce64c80f9e22f6ed45afd09323c0`
- one control-plane and two worker nodes
- distinct temporary host directories mounted at `/mnt/shiftpv` on each worker
- Helm `v3.15.2`
- temporary Colima Docker engine `29.5.2` on arm64

## Command

```bash
./test/e2e/kind/run.sh
```

## Proven behavior

1. The image built successfully and loaded on all three kind nodes.
2. The Helm release installed one ready Controller Pod and two ready Node Pods;
   each Pod had all three containers ready.
3. both worker `CSINode` objects registered `csi.shiftpv.io` with
   `topology.csi.shiftpv.io/node`; the control-plane did not register the driver.
4. The chart marked `shiftpv` as the default StorageClass. A 64Mi RWO
   Filesystem PVC that omitted `storageClassName` was defaulted to `shiftpv`.
5. A Pod using that PVC reached Ready and wrote through the mounted volume. The
   PV used CSI driver `csi.shiftpv.io`, `Retain`, owner-node volume context,
   owner-node affinity, and `shiftpv.io/capacity-enforcement: none`.
6. The workload wrote a payload whose SHA-256 was
   `8c328652070131b5d4cdd29e7cc17f8eef6e9fbfa576425c9f71450cc2537f95`.
7. Deleting and recreating the Pod retained the same checksum on the same owner
   node, exercising NodeUnpublish and NodePublish.
8. After stopping the workload and running `helm uninstall`, the PVC, PV,
   reservation ConfigMap, and host payload file remained with the same checksum.
9. Reinstalling the release into the same namespace and recreating the Pod
   recovered the same PV, volume ID, owner node, and checksum.
